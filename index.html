Once you hand a goal to an agent, the world keeps changing: flights are delayed, prices shift, and plans are revised.

A GUI agent pays for every change in screen navigation,
so it falls further behind as changes accumulate.

An OS-native agent is an agent recognized by the operating system and integrated into its native state, capability, and trust mechanisms. It learns of changes as they happen, operates directly on application records, and acts under device-enforced authorization; its harness connects each change to the delegation it affects.

Why GUI agents fall behind

Keeping a delegated goal on track means following every change that affects it. Through the screen, each follow-up costs page visits and model calls, for every open delegation. A GUI agent either checks rarely and misses changes, or checks often and spends many calls.

1Perceive changes

Through the GUIMany changes, such as a price drop or an edited record, raise no notification and appear only on their page. A notification must be verified in the app, and the agent cannot tell which delegation it concerns, so it re-checks every one.

OS-nativeThe OS delivers notifications, application events, and device changes as they happen. The harness wakes only the task a change affects.

2Operate reliably

Through the GUIEach follow-up must find the booking or thread again on screens designed for people. Every revision repeats a multi-step navigation, and a similar-looking entry can lead to the wrong record.

OS-nativeApplications expose functions with structured arguments and results. The agent acts on the records its task created, by reference.

3Act within authorization

Through the GUIA screen does not show which operations are irreversible or which fields are private, so the model's judgment alone decides when to pay or share.

OS-nativeApplications declare side effects and private data, and the OS checks identity and permissions. Sensitive calls run only under a task's grant or the user's approval.

The OS already holds what all three require, but it does not know what the user has delegated. The OS-native agent harness makes that connection.

OS-native agents

The OS provides native state, capabilities, and trust, but serves one call at a time. Our harness keeps each delegation as a task, wakes it when a change matters, and acts within the authorization granted to it. State observation and permission checks run on the device without the model, so the model is invoked only when a task needs a decision.

Persistent tasks. A delegation can last for hours and span several conversations. Each one is kept as a task record, separate from the sessions that execute it, holding the goal, constraints, progress, and references to the records it created. A woken task resumes with only what changed, so the user never restates the trip.

What the OS providesHow our harness uses it

Native state

Application records, device conditions, and notifications, delivered as they occur, including between model turns.

Perception and wake-up

Monitors bound to tasks feed a change log. A short assessment wakes only the affected task: the 4-hour delay costs about 1.6K tokens, not a full agent turn.

Native capabilities

AppFunctions and system APIs, described in a catalog with arguments, results, side effects, and private data. GUI actions remain where no function exists.

Dynamic tool loading

A session starts with a few system tools; loading a skill reveals only the functions it declares. The context stays small and calls reach the right records.

Native trust

Android identity and permissions, trusted on-device confirmation, local filling of personal data, and a hash-chained audit log.

Task-scoped authorization

Calls are classed as observations, changes, or sensitive. Changes and sensitive calls need a grant for their task or the user's approval; grants expire when the task closes.

DynamicWorld

Existing mobile benchmarks check whether a request is completed from a given state, so they cannot reveal a delay that goes unnoticed, a booking changed in the wrong record, or a reminder sent after the user said stop. DynamicWorld places four to six related delegations on one Android phone with 18 apps while applications, the system, time, and the user change on a replayable timeline.

Shared state

Delegations overlap over common people, records, and budgets; 23 events each affect two to four tasks at once.

Replayable changes

App updates, device conditions, time, and user revisions follow one timeline from the same initial state, with distractors such as stale confirmations.

Windowed checks

Each requirement is checked in the period it applies: 540 task-stage checks catch missed opportunities and unauthorized steps that a final state would hide.

Challenge definitions
Intent clarification
Resolves unclear objects or requirements through context, queries, or the user, and keeps the clarified requirements in later actions.
Info. integration
Combines related facts from several sources into a result that satisfies the applicable constraints.
Timely action
Keeps a standing delegation, obtains current information through later checks or monitoring, and acts when its time or conditions are met. Tests perceiving changes.
Plan adaptation
Revises existing arrangements as facts or requirements change while preserving unaffected results. Tests operating on existing records.
Authorized execution
Distinguishes permitted recipients, information, purposes, and actions under the current authorization. Tests acting within authorization.
Routine execution
Carries out a clearly specified request with sufficient information.

Getting started

Linux x86_64 with KVM. We recommend 16 GB RAM and 50 GB free disk, plus a model service with tool-call support.

Setup prepares host tools and builds the research apps locally. Configure your model in .env, start the phone, then enter a task in OS-native Agent.

Setup guide ↗
Quick start
git clone https://github.com/FreedomIntelligence/OSNativeAgent.git
cd OSNativeAgent
bash osnative setup

# Configure your model service in .env
bash osnative start
